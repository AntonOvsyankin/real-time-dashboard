# Realtime Fintech Dashboard

An Angular 22 single-page app that shows live, cumulative market metrics for up to 50 fictional instruments. Market updates are generated by a **Rust library compiled to WebAssembly**, which runs inside a **Web Worker**. The worker aggregates the updates and sends small per-instrument snapshots to Angular.

- **Live demo:** `https://<github-user>.github.io/real-time-dashboard/` (placeholder until the repository is published)
- **Repository:** `https://github.com/<github-user>/real-time-dashboard` (placeholder)

Two routes:

- `/dashboard`: a live table with Last price, Bid–ask spread, Volume, VWAP and Order-book imbalance for each instrument, a Pause/Resume button, and a producer status panel.
- `/settings`: a validated form (instrument count 1–50, updates per batch 1–1,000, batch interval 50–2,000 ms; defaults 5 / 100 / 500) with an **Apply** button. Edits take effect only when you click Apply. Applying starts a new run.

## 1. Architecture

```
┌──────────────────────── Main thread (Angular) ────────────────────────┐
│ SettingsPage ──apply(settings)──▶ ProducerService (root, signals)       │
│ DashboardPage ◀──signals: metrics, status, runId, totals──┘   │  ▲       │
│   Pause/Resume ──pause()/resume()──────────────────────────▶ │  │       │
└──────────────────────────────────────── postMessage(cmd) ─────┘  │ events│
                                                                   │ (runId│
┌──────────────────────── Web Worker ─────────────────────────────▼──┴───┐
│ producer.worker.ts → ProducerEngine(handle cmd)                          │
│   ├─ WasmMarketGenerator (instantiate .wasm, gen_create, gen_generate)   │
│   ├─ MetricsAccumulator  (cumulative totals, typed arrays)               │
│   └─ Scheduler (setTimeout chain; injected in tests)                     │
└──────────────────────────────────────────────────────────────────────────┘
                       ▲ Int32Array view over Wasm memory
┌──────────── Wasm (Rust, wasm32-unknown-unknown) ────────────┐
│ MarketGenerator: SplitMix64 RNG, per-instrument mid/spread/  │
│ book qty state, fixed record buffer [MAX_BATCH * 7] i32      │
└──────────────────────────────────────────────────────────────┘
```

### Why the worker does the aggregation

Three options were considered:

| Approach | Trade-off |
|---|---|
| **A. Wasm generates, worker aggregates, Angular renders snapshots (chosen)** | Main-thread work does not depend on the update rate: at most 20 snapshots/s with at most 50 rows each. The formulas are plain TypeScript and easy to unit test. |
| B. Worker forwards raw batches, Angular aggregates | Simplest worker, but main-thread work grows with the rate (up to 20,000 updates/s), which risks jank. |
| C. Wasm generates and aggregates | Fastest, but the metric logic and its tests move to Rust and reset semantics cross the Wasm boundary. |

### Run isolation (`runId`)

`ProducerService` owns a monotonically increasing `runId`. Every `start`, `pause` and `resume` command carries it, the worker tags every `snapshot` and `status` event with it, and the service **drops any event whose `runId` is not the current one**. Apply increments `runId`, resets the table to empty rows immediately, and sends `start`. A late snapshot from the previous run can never overwrite the new run.

Exactly one worker exists at a time. `ProducerService.init()` is idempotent and runs once from `provideAppInitializer`. Components never create workers, so navigating between pages keeps the run going (or paused). The only other place a worker is created is **Retry** after a load failure, and it terminates the old worker first.

### Binary record layout (Wasm ⇄ worker)

Each update is 7 consecutive `i32` values in a buffer inside Wasm linear memory. The worker reads them through an `Int32Array` view (no copy).

| Offset | Field | Meaning |
|---|---|---|
| 0 | `instrumentIndex` | 0..instrumentCount-1 (symbols are fixed by index) |
| 1 | `priceCents` | trade price; equals the bid or the ask |
| 2 | `tradeQuantity` | > 0 |
| 3 | `bidCents` | > 0 |
| 4 | `askCents` | > bid |
| 5 | `bidQuantity` | >= 0 |
| 6 | `askQuantity` | >= 0 |

### Wasm ABI

| Export | Signature | Behavior |
|---|---|---|
| `gen_abi_version` | `() -> u32` | Returns `1`; the worker refuses other versions. |
| `gen_record_stride` | `() -> u32` | Returns `7`; the worker checks it. |
| `gen_create` | `(instrument_count: u32, seed: u32) -> i32` | Replaces (frees) any existing generator. `0` = OK, `-1` = count outside 1..=50. |
| `gen_generate` | `(count: u32) -> i32` | Writes `count` records. Returns `count`, `-2` (count outside 1..=1000) or `-3` (no generator). |
| `gen_buffer_ptr` | `() -> u32` | Byte offset of the record buffer in `memory` (re-read after every call). |
| `gen_destroy` | `() -> ()` | Frees the generator. |
| `memory` | memory | Linear memory. |

The module has **no imports** and is instantiated with `{}`.

### Why there is no wasm-bindgen

The boundary is a handful of functions that take and return integers, plus one shared buffer. A hand-written `extern "C"` ABI needs zero crate dependencies and zero generated JS glue, builds with plain `cargo build --target wasm32-unknown-unknown` (no wasm-pack), and lets the worker read batches zero-copy. The whole module is about 23 KB.

## 2. Generator model

All randomness and price logic lives in Rust (`wasm/market-generator/src/generator.rs`), driven by a seeded SplitMix64 PRNG. Each instrument keeps its own state between batches:

- **Start:** mid price $20–$500, bid and ask book quantities 100–2,000.
- **Per update:** pick a random instrument (repeats allowed), then:
  1. **Random walk:** move the mid by up to ±0.1% (at least 1 cent), clamped to $1.00–$100,000.00.
  2. **Spread:** 1 cent up to mid/2,500; `bid = mid - spread/2`, `ask = bid + spread`, so `bid > 0` and `ask > bid` always.
  3. **Trade:** at the bid or the ask (coin flip), quantity 1–100.
  4. **Book:** bid and ask quantities each move by ±150, clamped to 0–5,000 (zero is reachable).

## 3. Metrics and precision

For each instrument, over the whole current run (cumulative, not a rolling window):

| Metric | Definition | Unavailable when |
|---|---|---|
| Last price | price of the latest trade | no trade yet |
| Bid–ask spread | `ask - bid` of the latest snapshot | no data yet |
| Volume | sum of trade quantities (book quantities never count) | shows `0` before data |
| VWAP | `sum(price × qty) / sum(qty)` | volume is 0 |
| Imbalance | `(bidQty - askQty) / (bidQty + askQty)`, in −1..+1 | no data yet, or both quantities are 0 |

- All prices are **integer cents** end to end. Rounding happens only for display (`$101.50`; VWAP is kept unrounded internally).
- Volume and notional are JavaScript `number`s. They are exact up to 2^53, which is more than 24 hours at the maximum rate with realistic prices; beyond that the relative error is about 1e-16, invisible after 2-decimal rounding.
- No event history is kept: the worker folds each record into per-instrument typed arrays and discards it.
- Unavailable values show as an em dash `—` with `aria-label="unavailable"`. Imbalance is shown with an explicit sign (`+0.20`, `-0.35`, `0.00`).


## 5. Commands

```bash
npm ci               # install dependencies
npm start            # build the Wasm module, then ng serve on http://localhost:4200/
npm run build        # build the Wasm module, then a production build into dist/real-time-dashboard/browser
npm run build:wasm   # only build the Wasm module into public/wasm/
npm run test:wasm    # Rust unit tests (cargo test)
npm run test:ci      # Angular unit tests (Vitest, single run)
npm run test:all     # both
```

`public/wasm/market_generator.wasm` is a build output and is not committed; `npm start` and `npm run build` create it.

## 6. Deployment

GitHub Actions (`.github/workflows/ci-deploy.yml`) runs on every push and pull request: Rust tests, Angular tests, Wasm build, and an Angular build with `--base-href "/<repo-name>/"` (taken from the repository name). On pushes to `main`, the build is published to **GitHub Pages**. `index.html` is copied to `404.html` so deep links such as `/real-time-dashboard/settings` survive a reload.

One-time setup: in the repository, go to **Settings → Pages** and set **Source = GitHub Actions**.

Building locally with a base href from Git Bash on Windows needs `MSYS_NO_PATHCONV=1`, because Git Bash rewrites arguments that look like paths (`/real-time-dashboard/`).

## 8. Assumptions and decisions

- **A1. Producer status** shows the state (`Initializing…`, `Running`, `Paused`, `Error`), run number, applied settings, nominal rate, total updates in the current run, and the error message if any.
- **A2. Symbols** are fixed by instrument index (a list of 50); the Wasm sends the index.
- **A3. Display:** imbalance with a sign and 2 decimals, prices as USD with 2 decimals, volume as an integer with thousands separators, unavailable values as `—`.
- **A4. Apply** is enabled whenever the form is valid, even if unchanged; applying identical values still starts a fresh run.
- **D11. Unapplied edits** are discarded when you leave Settings; on return the form shows the currently applied settings.
- **D12. Errors are recoverable.** `run-error` (the Wasm is fine but a run failed): Apply starts a fresh run. `init-error` (worker or Wasm failed to load, or the worker crashed): a **Retry** button replaces the worker and starts a new run with the applied settings. Pause/Resume is disabled in both states; Apply is disabled only in `init-error`.
- **D13. Timing:** the first batch is generated immediately on start and on resume, then every interval. The paused period is never generated afterwards (no catch-up).
- **D14. Precision:** totals are JavaScript numbers (see section 3).

## 9. Performance notes

- One snapshot per batch: at most 20 per second (50 ms interval), each at most 50 rows, regardless of how many updates a batch contains.
- The worker reads Wasm output zero-copy through an `Int32Array` view; the record buffer is allocated once per run.
- Aggregation uses typed arrays and no per-update allocations.
- Angular renders with signals, `OnPush` components and zoneless change detection; the table is a native `<table>` with `track row.symbol`.
- The batch timer compensates for processing time (`interval - elapsed`), so the nominal rate holds at high load.
